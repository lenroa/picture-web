Opening

Agent 的本质不是“会聊天”，而是能在一个具体场景里 持续完成任务。

判断标准：是否减少人的判断负担、操作步骤和跨系统切换。

Five Moves

把 Agent 当成一个新产品，而不是一个新功能

01

场景发掘

找高频、刚需、痛感清晰的任务。

02

选择模型

按推理、速度、成本、工具调用拆解。

03

MVP 验证

先验证闭环，不急着做大平台。

04

种子用户

找到愿意共创、给数据、忍受粗糙的人。

05

商业化

围绕结果、节省时间和风险降低收费。

Scene Discovery

好场景通常藏在“重复但不简单”的工作里

别从“AI 能做什么”出发，从“人每天被什么拖住”出发。

  • 任务频繁发生，且每次都有相似输入和相似产出。
  • 过程需要判断、搜索、整理、调用工具或跨系统操作。
  • 现有方案靠人工、Excel、复制粘贴或群聊推动。
  • 失败成本可控，但做得好会明显省时间或提升质量。
Opportunity Filter

用四个问题过滤伪需求

01

谁在痛？

角色越具体越好：运营、销售、客服、财务、研究员，而不是“所有人”。

02

痛在哪里？

是找资料、做判断、写内容、填系统，还是协调下一步。

03

现在怎么做？

替代方案越笨重，Agent 越容易切入。

04

凭什么付费？

时间、收入、合规、客户体验，至少要命中一个经济指标。

05

数据从哪来？

Agent 需要上下文：文档、工具权限、历史记录、用户反馈。

06

如何评估？

定义正确率、节省时间、采纳率、人工接管率。

Model Choice

选模型不是选“最强”，而是选任务组合

规划

多步骤拆解、策略判断、异常处理。需要强推理，允许稍慢。

执行

调用工具、格式转换、批量处理。需要稳定、便宜、可并发。

交互

对话澄清、解释结果、收集反馈。需要低延迟和好语气。

评估

判断输出是否合格、是否需要人工接管。需要独立校验。

实践建议：用强模型做规划和疑难判断，用轻模型做重复执行，用规则兜底高风险动作。

MVP Design

MVP 要验证闭环，而不是展示魔法

  • 选择一个窄任务：例如“把销售通话整理成 CRM 跟进计划”。
  • 只接必要工具：输入、检索、生成、写回、通知。
  • 保留人工确认：让用户看见可控性，也收集训练信号。
  • 定义失败出口：不确定就澄清，高风险就转人工。
  • 记录每次结果：采纳、修改、放弃、错误原因。
Validation Metrics

不要只看“准确率”，要看工作有没有真的变短

采纳率

用户是否直接使用 Agent 的结果，还是每次都重写。

节省时间

从开始任务到完成任务，平均缩短多少分钟。

接管率

多少任务需要人工介入；介入发生在哪个步骤。

复用率

同一用户是否在第二天、第二周继续使用。

单位成本

每次成功任务的模型、检索、工具和人工成本。

Seed Users

种子用户不是流量，而是共同建模的人

早期别追求“很多人试用”，要找能让你看见真实工作流的人。

  • 他们有强痛点，愿意把真实任务给你看。
  • 他们能快速反馈什么可用、什么不可信。
  • 他们愿意忍受粗糙界面，但不能忍受无效结果。
  • 他们所在组织里有扩散路径和预算线索。
Commercialization

Agent 的收费逻辑：不要卖 Token，卖结果

Seat

适合协作软件、团队助手、工作台入口。简单，但容易被用量成本挤压。

Usage

按任务数、线索数、工单数收费。适合价值和使用量强相关的场景。

Outcome

按节省成本、成交结果、风险降低收费。最有想象力，也最难定义归因。

Workflow

绑定一个完整流程收订阅费：数据接入、执行、审计、报表都在里面。

Guardrails

越像员工，越需要边界

  • 权限最小化：只给完成任务所需的工具和数据。
  • 关键动作确认：发邮件、改数据、付款、对外承诺都要有审批。
  • 可追溯日志：保存输入、检索证据、工具调用和最终输出。
  • 评估集常更新：把真实失败案例变成回归测试。
  • 用户预期管理：明确它擅长什么、不能替代什么。
Action Plan

30 天做出第一个可收费 Agent

第 1 周

访谈 10 个目标用户，记录高频任务、现有流程和付费触发点。

第 2 周

做单任务 Demo：输入真实数据，输出可直接使用的结果。

第 3 周

接入一个关键工具，跑 20 次真实任务，统计采纳和接管。

第 4 周

找 3 个种子客户试付费，用价格测试价值假设。

Closing

创建 Agent 的关键，是把不确定的智能，放进 确定的工作流。
